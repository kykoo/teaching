ROSEHIPS Event-driven DAQ protocol

ver 1

1 Overview

This document defines an MQTT-based, event-driven DAQ protocol for ROSEHIPS HGM-monitoring deployments. The protocol specifies how the cloud control service, charge controllers, Raspberry Pi camera hosts, accelerometer nodes, and wind nodes communicate through an MQTT broker.

The protocol supports multiple deployments at any given time. Each deployment is addressed independently and is orchestrated by the cloud control service.

A deployment is one fielded ROSEHIPS DAQ system installed to monitor an HGM. It may contain:

  • n camera subsystems, each composed of a charge controller, a Raspberry Pi, and a camera
  • m accelerometer nodes
  • k wind nodes

The protocol uses two control patterns:

  1. Ground Nodes: Charge controllers are always online and respond to retained desired-state MQTT messages.
  2. Mast Nodes: Accelerometer and wind nodes are normally asleep, wake periodically, and consume retained 3-hour DAQ-window MQTT messages.

The control service is a cloud-hosted service outside the field deployment. For each deployment, it evaluates current and forecast wind speed and direction, then publishes retained MQTT commands and schedules that tell field nodes when to start DAQ, stop DAQ, or remain idle.

The protocol is intended to be:

  • event-driven
  • explicit about time windows
  • robust to MQTT retransmission and retained-message replay
  • compatible with low-duty-cycle sleeping nodes
  • auditable from broker traffic and node reports

A MQTT server is available for ROSEHIPS Project. See MQTT Broker Access Example for details.

2 Scope and Conventions

  • All timestamps shall use UTC in ISO 8601 format, for example 2026-04-02T03:00:00Z.
  • All command and report topics should use MQTT QoS 1 (see appendix).
  • Topics consumed by sleeping nodes shall be retained.
  • Each command or schedule shall carry a unique identifier.
  • Nodes shall treat repeated receipt of the same identifier as a duplicate and shall not repeat hardware side effects.
  • Each node shall publish sufficient reports for the control service to reconstruct the executed DAQ state.

3 System Model

There can be multiple deployments at any given time. Each deployment is addressed independently through set_id.

A deployment may provision n camera subsystems, m accelerometer nodes, and k wind nodes, where n, m, and k are deployment-specific and are not fixed by this protocol.

Example deployment identifiers are:

  • set1
  • set2
  • set3

3.1 Node identifiers

4 Part I. Charge-Controller Protocol

4.1 Applicability

This part applies to the always-online charge controllers that power the camera subsystems and to the Raspberry Pi hosts connected to those charge controllers. A deployment may contain n such subsystems, where n is deployment-specific and may be zero.

4.2 Topics

Topic Publisher Subscriber Retained Purpose
rosehips/<set_id>/camera/<node_id>/daq/desired control service charge controller, Raspberry Pi yes Desired DAQ state for the camera subsystem
rosehips/<set_id>/camera/<node_id>/controller/report charge controller control service no Relay, external-power, and shutdown-timeout reports
rosehips/<set_id>/camera/<node_id>/rpi/report Raspberry Pi control service, charge controller no Pi-side DAQ, shutdown, and inconsistent-state reports

For this part, <node_id> identifies one provisioned camera subsystem. Topics shall be published only for camera subsystems that are actually provisioned in the deployment.

In this part, the control service is the cloud-hosted orchestrator for the deployment. Its retained daq/desired publications are the output of a wind-informed decision process that considers current and forecast wind speed and direction when deciding whether camera DAQ should start or stop.

4.3 Payload fields and identifiers

All charge-controller commands and reports shall carry:

  • protocol_version
  • set_id
  • node_class
  • node_id
  • published_at
  • command_id for desired-state commands
  • session_id for correlation of one DAQ run across all related messages

command_id identifies one desired-state publication. session_id identifies the DAQ run that the start command, stop command, Raspberry Pi reports, and controller reports all belong to. A repeated message with the same command_id shall be treated as a duplicate. A changed session_id shall be treated as a new DAQ run.

4.5 Charge-controller behavior

When a charge controller receives desired_state = start_daq:

  1. If command_id has already been handled, it shall ignore the duplicate.
  2. If external power is off, it shall enable the relay and power the Raspberry Pi.
  3. It shall publish a controller report that external power has been applied.
  4. It shall NOT repeatedly power-cycle the subsystem for duplicate retained messages belonging to the same session_id.

When a charge controller receives desired_state = stop_daq:

  1. It shall NOT cut relay power immediately.
  2. It shall wait up to 5 minutes for either shutdown_started or inconsistent_state_shutdown_started on rosehips/<set_id>/camera/<node_id>/rpi/report.
  3. If either event is received for the active session_id, it shall wait (n: Miaomin, what would be good for this?) seconds.
  4. If neither event is received within 5 minutes, it shall publish a controller report with event = "shutdown_timeout".
  5. It shall then turn the relay off.
  6. It shall publish a controller report that external power has been removed.

4.6 Raspberry Pi behavior

When the Raspberry Pi sees desired_state = start_daq for a new session_id:

  1. It shall start the camera DAQ process.
  2. It shall publish a report confirming DAQ start.

When the Raspberry Pi sees desired_state = stop_daq for the active session_id:

  1. It shall stop DAQ cleanly.
  2. It shall publish shutdown_started.
  3. It shall shut the operating system down.

If the Raspberry Pi boots or wakes, reads retained desired_state = stop_daq, and finds that the referenced DAQ session is not running locally:

  1. It shall publish inconsistent_state_shutdown_started.
  2. It shall shut the operating system down.

4.8 Sequence summary

Start sequence:

  1. The control service determines from current and forecast wind speed and direction that camera DAQ should begin, then publishes retained desired_state = start_daq.
  2. The charge controller applies relay power to the Raspberry Pi.
  3. The Raspberry Pi boots, reads retained desired state, and starts DAQ.
  4. The Raspberry Pi publishes daq_started.

Stop sequence:

  1. The control service determines from current and forecast wind speed and direction that camera DAQ should stop, then publishes retained desired_state = stop_daq.
  2. The Raspberry Pi stops DAQ and publishes shutdown_started.
  3. The charge controller waits (n: Miaomin, what would be good for this?) seconds.
  4. The charge controller removes relay power and publishes relay_power_off.

Retained-stop wake sequence:

  1. The control service publishes retained desired_state = stop_daq.
  2. The Raspberry Pi boots or wakes, reads the retained desired state, and finds that the referenced DAQ session is not running locally.
  3. The Raspberry Pi publishes inconsistent_state_shutdown_started.
  4. The Raspberry Pi shuts down.
  5. The charge controller waits 180 seconds.
  6. The charge controller removes relay power and publishes relay_power_off.

Stop-timeout sequence:

  1. The control service publishes retained desired_state = stop_daq.
  2. If the Raspberry Pi does not publish either shutdown_started or inconsistent_state_shutdown_started within 5 minutes, the charge controller publishes shutdown_timeout.
  3. The charge controller removes relay power and publishes relay_power_off.

5 Part II. Accelerometer and Wind Node Protocol

5.1 Applicability

This part applies to the periodically waking accelerometer and wind nodes. A deployment may contain m accelerometer nodes and k wind nodes, where m and k are deployment-specific and may be zero.

5.2 Topics

Topic Publisher Subscriber Retained Purpose
rosehips/<set_id>/<class>/<node_id>/daq/window control service accelerometer or wind node yes DAQ plan for the next 3 h window
rosehips/<set_id>/<class>/<node_id>/daq/report accelerometer or wind node control service no Wake, schedule, DAQ start, DAQ stop, and sleep reports

In these topics, <class> shall be acc or wnd. Topics shall be published only for nodes that are actually provisioned in the deployment.

The same cloud-hosted control service produces these retained 3-hour schedules. It uses current and forecast wind speed and direction to decide whether each upcoming window should contain a DAQ run or explicitly publish plan_type = none.

5.3 Payload fields and identifiers

All accelerometer and wind schedule messages and reports shall carry:

  • protocol_version
  • set_id
  • node_class
  • node_id
  • published_at
  • schedule_id for the published 3-hour DAQ window
  • session_id when the window contains an actual DAQ run

schedule_id identifies one published 3-hour DAQ window. session_id identifies the DAQ run within that window and shall be reused unchanged by node reports associated with that run. A repeated message with the same schedule_id shall be treated as a duplicate.

5.4 Schedule publication rules

For each deployment and provisioned node, the control service shall evaluate current and forecast wind speed and direction before deciding whether the next 3-hour interval should contain a DAQ run.

The control service shall publish one retained payload every 3 hours, aligned to:

  • 00:00 UTC
  • 03:00 UTC
  • 06:00 UTC
  • 09:00 UTC
  • 12:00 UTC
  • 15:00 UTC
  • 18:00 UTC
  • 21:00 UTC

After making that decision, each payload shall explicitly describe the interval [window_start, window_end) and shall explicitly indicate whether a DAQ run exists inside that interval. If no DAQ run is planned inside the next 3-hour window, the payload shall explicitly state plan_type = none. Silence is not a valid schedule.

The same structure applies to wind nodes, with node_class = "wnd" and a wind-node topic. For each provisioned wind node, the control service shall publish a retained schedule on that node’s topic.

5.6 Node behavior

On each periodic wake:

  1. The node shall connect to the network and broker.
  2. The node shall read the retained daq/window payload for its own topic.
  3. If plan_type = none, the node shall publish a report and return to sleep.
  4. If plan_type = daq_window and now < daq_start, the node SHOULD sleep until just before daq_start.
  5. The node shall start DAQ at daq_start.
  6. The node shall stop DAQ at daq_stop.
  7. The node shall publish stop and summary reports.
  8. The node shall sleep until the next periodic wake or internal deadline.

5.7 Validity rules

The node shall ignore a retained schedule if:

  • window_end <= now
  • daq_stop <= daq_start
  • the schedule_id was already completed

Nodes SHOULD reject schedules whose time interval is invalid. Nodes SHOULD prefer RTC-corrected or GNSS-corrected UTC time when available. If local time is not trustworthy, a node SHOULD publish a time_invalid report rather than executing a speculative DAQ window.

5.9 Sequence summary

  1. The node wakes on its normal 3-hour schedule.
  2. The node fetches the retained daq/window payload.
  3. The node either returns to sleep immediately or arms itself for the DAQ interval contained in the payload.
  4. The node starts and stops DAQ according to the scheduled window.
  5. The node publishes completion reports and returns to sleep.

6 Version 1 Profile

The minimum conforming version of this protocol shall implement the following:

  • retained desired-state topics for provisioned charge controllers
  • retained 3-hour DAQ window topics for provisioned accelerometer and wind nodes
  • a cloud-hosted control service that turns wind-based operational decisions into retained MQTT commands and schedules
  • UTC timestamps in every command, schedule, and report payload
  • explicit plan_type = none messages for empty accelerometer and wind windows
  • mandatory shutdown_started reporting from the Raspberry Pi, plus timeout-based forced power removal if that report is missing
  • stable session_id values across all payloads belonging to the same DAQ run
  • support for deployments that provision n camera subsystems, m accelerometer nodes, and k wind nodes

7 Appendix. MQTT QoS 1 Semantics

MQTT QoS 1 provides at-least-once delivery between broker and client. A sender publishes a message and expects a PUBACK from the receiver. If the acknowledgement is not observed, the sender may retransmit the same MQTT message.

For this protocol, QoS 1 is selected because:

  • command and schedule messages are important enough that best-effort delivery is insufficient
  • sleeping nodes may only be online briefly, so message loss during that window is costly
  • duplicate delivery is acceptable when protocol payloads are idempotent

Operational consequences:

  • a node may receive the same retained or retransmitted payload more than once
  • the protocol therefore requires command_id, schedule_id, and session_id to support duplicate detection and correlation
  • nodes shall treat repeated receipt of the same command or schedule identifier as a replay, not as a new hardware action
  • QoS 1 does not guarantee exactly-once execution; it guarantees delivery with possible duplicates

QoS 1 is therefore paired with idempotent node behavior. Delivery reliability is provided by MQTT, while duplicate suppression is provided by the protocol state machine in each node.

8.1.1 Source code: camera1_publish_daq.py

#!/usr/bin/env python3
"""Publish a retained DAQ desired-state command for ROSEHIPS set1 camera1."""

from __future__ import annotations

import argparse
import json
import ssl
import sys
import uuid
from datetime import datetime, timezone

try:
    import paho.mqtt.client as mqtt
except ImportError as exc:  # pragma: no cover - import guard
    raise SystemExit(
        "This script requires paho-mqtt. Install it with: pip install paho-mqtt"
    ) from exc


BROKER_HOST = "mqtt.shmcloud.org"
BROKER_PORT = 8883
BROKER_USERNAME = "mqtt-client"
BROKER_PASSWORD = "hXlOooy6yTdT8IW3hyNbokkN"

TOPIC = "rosehips/set1/camera/camera1/daq/desired"

PROTOCOL_VERSION = "1.0"
SET_ID = "set1"
NODE_CLASS = "camera"
NODE_ID = "camera1"

ACTION_TO_DESIRED_STATE = {
    "start": "start_daq",
    "stop": "stop_daq",
}


def utc_now() -> datetime:
    return datetime.now(timezone.utc)


def isoformat_z(ts: datetime) -> str:
    return ts.astimezone(timezone.utc).strftime("%Y-%m-%dT%H:%M:%SZ")


def default_session_id(ts: datetime) -> str:
    return "session-" + ts.astimezone(timezone.utc).strftime("%Y%m%dT%H%M%SZ")


def command_id(ts: datetime) -> str:
    return f"{NODE_ID}-cmd-{ts.astimezone(timezone.utc).strftime('%Y%m%dT%H%M%SZ')}"


def build_payload(action: str, session: str) -> str:
    now = utc_now()
    payload = {
        "protocol_version": PROTOCOL_VERSION,
        "set_id": SET_ID,
        "node_class": NODE_CLASS,
        "node_id": NODE_ID,
        "command_id": command_id(now),
        "session_id": session,
        "desired_state": ACTION_TO_DESIRED_STATE[action],
        "published_at": isoformat_z(now),
    }
    return json.dumps(payload, separators=(",", ":"))


def make_client(action: str) -> mqtt.Client:
    client = mqtt.Client(
        callback_api_version=mqtt.CallbackAPIVersion.VERSION2,
        client_id=f"{NODE_ID}-{action}-{uuid.uuid4().hex[:8]}",
        protocol=mqtt.MQTTv311,
    )
    client.username_pw_set(BROKER_USERNAME, BROKER_PASSWORD)
    client.tls_set(tls_version=ssl.PROTOCOL_TLS_CLIENT, cert_reqs=ssl.CERT_REQUIRED)
    return client


def publish(action: str, payload: str) -> None:
    client = make_client(action)
    client.connect(BROKER_HOST, BROKER_PORT, keepalive=60)
    client.loop_start()
    try:
        info = client.publish(TOPIC, payload=payload, qos=1, retain=True)
        info.wait_for_publish()
        if info.rc != mqtt.MQTT_ERR_SUCCESS:
            raise RuntimeError(f"MQTT publish failed with rc={info.rc}")
    finally:
        client.loop_stop()
        client.disconnect()


def parse_args() -> argparse.Namespace:
    parser = argparse.ArgumentParser()
    parser.add_argument(
        "action",
        choices=sorted(ACTION_TO_DESIRED_STATE),
        help="Publish either start_daq or stop_daq.",
    )
    parser.add_argument(
        "--session-id",
        help=(
            "Session identifier to publish. Use the same value for the matching "
            "start and stop commands. Defaults to a UTC timestamp-based value."
        ),
    )
    return parser.parse_args()


def main() -> int:
    args = parse_args()
    session = args.session_id or default_session_id(utc_now())
    payload = build_payload(args.action, session)
    publish(args.action, payload)
    print(f"Published {ACTION_TO_DESIRED_STATE[args.action]} to {TOPIC}")
    print(f"session_id={session}")
    return 0


if __name__ == "__main__":
    sys.exit(main())
